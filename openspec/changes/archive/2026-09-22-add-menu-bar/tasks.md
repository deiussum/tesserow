## 4. Exit and OS window-close

- [x] 4.1 Add a `File > Exit` handler in `app.tsx` that calls `getCurrentWindow().close()` from `@tauri-apps/api/window`, gated by the same dirty check and shared dialog as section 3
- [x] 4.2 Register a `getCurrentWindow().onCloseRequested()` listener (in `app.tsx` or `renderer.ts`) that calls `event.preventDefault()`, runs the same dirty check, and either opens the shared dialog (calling `.close()` again on confirm) or closes immediately when not dirty

  Implemented differently from this wording: `close()` re-triggers `onCloseRequested`, so calling it again on confirm would loop forever. The listener now only calls `preventDefault()` when dirty (matching Tauri's own documented pattern), and the shared dialog's confirm action calls `getCurrentWindow().destroy()` (a force-close that doesn't re-emit the event) instead of `close()`. `design.md` has been corrected to match - see its Decisions section. Observable behavior (confirmation before discarding, either entry point) is unchanged.
- [x] 4.3 Run `npm start` (`tauri dev`) and manually verify: Exit with a clean chart closes immediately; Exit with a dirty chart prompts; the OS titlebar close button behaves the same as Exit in both cases

  Confirmed by the user: Exit triggers the dirty check and closes correctly, and the OS titlebar close button's discard path (Discard actually closes the window) works too.
- [x] 4.4 If the manual check in 4.3 shows the close-requested event isn't firing, add the specific `core:window:*` permission(s) needed to `src-tauri/capabilities/default.json` and re-verify

  Root cause of "Exit does nothing" and "Discard doesn't close the window": `core:window`'s default permission set (checked against the vendored `tauri` crate's `permissions/window/autogenerated/reference.md`) does not include the `close` or `destroy` commands - only read-only/query commands are on by default. Both invokes were silently rejected (wrapped in `void ...()`, so the rejection was swallowed). Added `core:window:allow-close` and `core:window:allow-destroy` to `src-tauri/capabilities/default.json`. `cargo check` passes with the new capability entries.

## 9. QA round 2 fixes (found during the user's manual testing)

- [x] 9.1 File > Close now goes through the same discard-confirmation dialog as New/Open/Import/Exit/OS-close, instead of closing unconditionally. Reverses an earlier explicit decision (see `design.md` Non-Goals) after the user found the inconsistency surprising in practice. `mosaicClosedClicked` in `app.tsx` now wraps its body in `runWithDirtyGuard`; `specs/app-shell/spec.md` and `specs/mosaic-domain-model/spec.md` updated to match; test coverage added in `app.test.tsx`
- [x] 9.2 (pre-existing bug, unrelated to the menu-bar work, but blocked verifying this change's dirty-tracking across multiple mosaics) `Mosaic.setupCanvas()`'s click/hover listener attachment used a one-time boolean flag (`#eventListenersSet`), so only the very first `<canvas id="mosaic-canvas">` element in the app's lifetime ever got listeners - every canvas after a Close → reopen cycle was unclickable. Fixed by tracking the attached-to canvas by reference (`#canvasWithListeners`) instead of a boolean, so listeners reattach whenever `MosaicEditor` mounts a fresh canvas. Regression test in `Mosaic.canvas.test.ts`, confirmed to fail on the old code and pass on the fix
- [x] 9.3 File > New/Open/Import Image were wired as `disabled={props.mosaicOpen}` in `AppShell.tsx`, contradicting the "prompt to discard/close first" decision from exploration (they were supposed to stay enabled and go through the discard-confirmation flow already implemented in `app.tsx`'s `runWithDirtyGuard` - that logic was correct all along, only the UI blocked reaching it). Fixed by making New/Open/Import Image unconditionally enabled in `AppShell.tsx`; also fixed the Ctrl+N/Ctrl+O keyboard accelerators in `app.tsx`, which had the same bug (only fired when no mosaic was open). Updated `specs/app-shell/spec.md`'s "Top bar actions" and "keyboard accelerators" requirements; test coverage added in `AppShell.test.tsx` and `app.test.tsx`
- [x] 9.4 A consequence of 9.3: replacing an already-open mosaic via New/Open/Import skipped the zoom/pattern-panel/status/export-dialog reset that Close already did, since that reset lived inline in `mosaicClosedClicked` only. Per user decision, matched Close's behavior: extracted a shared `resetEditorSessionState()` helper in `app.tsx`, called at the point each of New/Open/Import/Close actually replaces the mosaic (`newMosaicCreated`, `loadMosaicClicked`'s success branch, `imagePreviewComplete`, and `mosaicClosedClicked`) - deliberately not at the point the guard first lets them proceed, so cancelling a sub-dialog (e.g. New Mosaic) afterward can't reset state out from under a mosaic that's still open. New requirement added to `specs/app-shell/spec.md`; regression test in `app.test.tsx`, confirmed to fail without the fix and pass with it
